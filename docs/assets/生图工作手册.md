## 1. 工作规则（必须遵守）

1. **每次发请求前，先跟用户确认提示词、模型、数量、预算。** 用户已明确授权的批量除外。
2. **API key 绝不写进仓库内任何文件，也不要打在命令行里。** 本仓库会推到公开 GitHub。
   key 在 `~/.avalon-llm-key`（权限 600），用时 `source` 进来。
3. `docs/assets/generated/` 已在 `.gitignore`，不入库。**所以定稿资产的提示词必须留在
   `docs/assets/prompts/`（入库）**，只写在 `generated/` 里的 `_配置.md` 等于没留档。
4. **图片 URL 24 小时后失效**，生成后立即下载存盘（脚本已处理，并且会校验完整性）。
5. **长任务要用能被通知的方式跑**。用 `nohup ... &` 会脱离 harness 的任务跟踪，
   跑完不会叫醒你，只能靠用户来问。

## 2. 接口

```
POST https://openproxy-cn.zuoyebang.cc/openproxy/rp/v1/images/generations
Header: Authorization: Bearer $LLM_API_KEY
```

| 简称 | 模型 ID | 用途 |
|---|---|---|
| `5pro` | `doubao-seedream-5-0-pro-260628` | **默认**。质感最好，但不支持组图 |
| `5` | `doubao-seedream-5-0-260128` | 需要组图时才用 |
| `4` | `doubao-seedream-4-0-250828` | 旧版，没用过 |

### 2.1 价格

| 分辨率 | 单价 |
|---|---|
| ≤ 261 万像素（1.5K 及以下） | ¥0.30 / 张 |
| > 261 万像素（1.5K 以上） | **¥0.60 / 张** |

本项目卡牌 `1728x2304` = 398 万像素，**都是 ¥0.60**。
`scripts/genlib.py` 的 `price_of(size)` 会自动算，进度条实时显示花费。

### 2.2 能力矩阵（实测，别信文档）

seedream **4.0 的官方文档不适用于 5 / 5pro**。实测：

| | 组图 `sequential_image_generation` | 参考图 `image` | 流式 |
|---|---|---|---|
| `5pro` | ❌ **任何取值都报错**，`auto` 和 `disabled` 都不行 | ✅ 单张 / 数组都收 | — |
| `5` | ✅ 三种组图模式都可用 | ✅ | ✅ 逐张返回 |

`5pro` 报错原文：`the parameter sequential_image_generation is not supported by the current model`。
所以在 `5pro` 上**这个字段必须整个省略**。

### 2.3 必须传的参数

| 项 | 说明 |
|---|---|
| `watermark` | **必须 `false`**。官方示例默认 `true` |
| `size` | **必须写显式像素**。传 `"2K"` 时比例由模型自定，同一个值可能返回 4:3 也可能 16:9 |
| 尺寸下限 | **总像素 ≥ 3,686,400**。低于此值报 `InvalidParameter` |
| 输出 | 只出 **JPEG，没有透明通道** |

### 2.4 并发

单次 `5pro` 请求约 **97 秒**。并发直接决定总时长：

| 并发 | 速率 | 81 张耗时 |
|---|---|---|
| 3 | 32 秒/张 | 40 分钟 |
| 10 | 约 10 秒/张 | 约 14 分钟 |

`CONC=10` 实测稳定无限流。用 `CONC` 环境变量调。

## 3. 接口的坑（每一条都真金白银踩过）

### 3.1 组图返回顺序不保证和提示词编号一致

提示词写「第 1 张是牌背、第 2 张是成功牌、第 3 张是失败牌」，返回的三张**不一定按这个顺序**。
实测两轮各 12 组，各有 4 组把第 2、3 张对调了，36 个文件名有 8 个是错的。

规律：第 1 张一直是对的，错的只在后面几张之间。但**别依赖这条规律**。
正确做法：**按内容复核，不要信索引**。本项目用底色判定（绿=成功、红=失败、中性=牌背）。

### 3.2 `5pro` 上提示词绝不能写「生成一组 N 张」

它不报错，而是**把 N 张卡片拼进同一张画布**，还带白色外框。
`5pro` 只能逐张生成，提示词里只描述一张图。

### 3.3 参考图的参数名只能是 `image`

试了 5 个常见名字，**5 个全部返回成功**，但只有 `image` 真的生效。
`image_url` / `reference_image` / `init_image` / `images` 被**静默忽略**——
不报错，当纯文生图跑掉，白花一次钱。

参考图要压到 768 宽再转 base64（原图 1728 宽转出来约 1.1MB，请求体太大）。

### 3.4 「背面设计图」会让模型画出实体卡的白边

第一版卡背提示词开头写的是「身份卡牌的**背面**设计图」，36 张里 **28 张长出白边**——
「背面」让模型去渲染一张实体卡的背面，于是画出卡纸白边。

换成任务牌验证过的措辞「**正面平视的卡面设计图**」就好了，模型把它理解成平面图案。
再补一句「边框之外到画面边缘之间仍然是深棕底色」，堵住金边框外圈留白。

### 3.5 内容审核会拦描述负面精神状态的词

「疯子」的描述用了「眼神涣散」「神态癫狂失态」，**三张全被拦**：

```
The request failed because the input text may contain sensitive information
```

改成**只写行为不写精神状态**就过了：「举止夸张放肆，衣衫松垮凌乱，双臂张开，仰头大笑，
目光飘向别处不与人对视」。同样能出那股劲，而且更具体。

### 3.6 进程中断会留下半张图

被杀时下载到一半的 JPEG 会静静躺在产物里，PIL 一读就炸，后面每一步都踩。
`genlib.save_verified()` 下载完当场校验，坏了直接删并报错。

## 4. 提示词方法论

### 4.1 只用正面描述，不要「不要 X」这种补丁

想避开某种效果时，直觉是加一句「不要 X」。**这既不可靠，也容易把模型推到反方向。**

实测：摩根勒菲要「邪恶女巫头目 + 潇洒女皇，不能猥琐」。第一版加了「英姿飒爽」
「英气逼人」「不妖冶不谄媚不猥琐」，结果**面部明显往男相走**——「英气」在中文语境里
对模型基本等同于男性化。改成纯正面描述「气度沉稳的女王，兼具女巫的神秘……
她是掌权者，不是阴谋者」就对了。

同批清掉的：`不丑化`→`五官俊朗，仪表堂堂`、`不狼狈不猥琐`→`冷峻，有威慑力`。

### 4.2 气质是角色属性，不是全局规则

早期把「不要挑逗性姿势、不要谄媚表情、不要猥琐神态」写进了 27 个角色共用的公共段，
等于**把所有角色的气质抹平成一种**，还删掉了该有的邪气。

**公共段只管画风、构图、材质、边框；气质写进各角色自己的描述。** 而且两头都要写死：

- 该有威仪的邪恶角色要明说，否则被「邪恶=丑」默认处理
- 该猥琐的也要明说，否则被「角色卡=体面」抹平

### 4.3 形象设计前必须先读游戏机制

`miniprogram/data/roleGuides.js` 的 `goal` 和 `warning` 是角色形象的依据，
**不要照着角色名想象**。踩过两次：

- **骗徒**：机制是被查验时可自选显示阵营（`gameCore.js` 里 `displayedFaction` 返回 `claim`），
  本事是**让人相信他**。我看到「骗徒」就画成宫廷弄臣——一眼就看出不可信，方向完全反了。
- **破坏者**：`roleGuides` 写的是「持有**退伍**领袖指示物后必须出失败牌」，
  「退伍」是游戏术语指**当过领袖之后被锁死**。我画成了拿工具的工匠。

### 4.4 皮肤 = 人物设计不同，不是同一个人换渲染

第一次做四种画风时，**27 个角色的形象描述一个字都没改**，只换风格段。
结果是「同一个人换四种渲染」——那是滤镜不是皮肤。

**每套皮肤要重写全部 27 个角色的形象**：轮廓、姿态、服装解读、年龄倾向、发色、构图，
全跟着画风走。同一个摩根，幻想华服里是银紫长发+夸张金属肩饰，木刻里是纯黑白排线
只有披风套色。

### 4.5 阵营辨识优先于角色辨识

木刻皮肤第一版给每个角色配了各自的套色（靛蓝/暗红/金黄/深绿/酒红/冷灰蓝…），
想的是「那点彩色是角色的记忆点」——**但这直接牺牲了阵营辨识**，而阵营才是玩家
真正要一眼看出的东西。

改成：**套色本身就是阵营色**（正义靛蓝 / 邪恶暗红），角色辨识交给画面内容。

### 4.6 套色对象的颜色本身要说得通，而且要够大

第二个错误：套色对象选了「教士的烛焰」「骗徒领口的宝石」。
烛焰染成蓝色不合理；宝石太小，淹在排线里根本看不见。

**规则：套色铺在人物最大的一块布料上**（披风/罩袍/大氅/圣带/斗篷内衬），
面积大、位置显眼、蓝或红都天然成立。只有本来就该是那个颜色且够大的物件才例外
（摩根掌心的火焰、盲眼杀手的蒙眼布、揭露者的灯光）。

### 4.7 一局能出现多次的角色需要多个变体

`cloudfunctions/avalonGame/gameCore.js` 的 `roleLimits`：

| 角色 | 上限 | 需要变体数 |
|---|---|---|
| `loyal` 忠臣 | `multiple`（10 人局正义方 6 人，最多 6 个） | 4 |
| `minion` 爪牙 | `multiple`（摩根 `required`，所以最多 3 个） | 3 |
| `duke` `archduke` `priest` `apprentice` | `maxCopies: 2` | 各 2 |

**同一条提示词的多次抽卡只是同一个人的不同角度，不是不同的人**，拿来当第二变体是糊弄。
每个变体必须有自己的形象描述。共同标识要保留（比如忠臣胸前的圆桌纹章），否则会散成
几个无关角色。

有变体的角色**不再出通用版**，直接出各变体。所以每套皮肤是 21 基础 + 15 变体 = 36 个形象。

### 4.8 必禁清单

```text
严禁出现：白色边框、白色四角、圆角外框、相框、画框、桌面、蜡烛、手、
任何环境或背景物体、卡片投影、文字、水印
```

不写这段，模型会把「卡牌」理解成「桌上一张卡牌的照片」，给你加相框、蜡烛、木桌。

### 4.9 提到一个东西就会被画出来，哪怕是在解释它不该出现

4.1 说的是「不要写『不要 X』」。有一个更隐蔽的版本：**在提示词里解释这张图将来会被
什么盖住，那些东西会被直接画进去。**

地面和首页底纹的公共段里写过一句纯解释性的话：

```text
座位标记、任务牌和文字都要压在这张图上面，所以它必须安静，不能抢戏。
```

结果两张图上撒满了**带数字的纸牌**。同一段的必禁清单里明明白白写着
「严禁出现：书本、任何道具或摆件、文字」，一点用没有——
**肯定句式的提及比否定清单强得多**，模型只记住了「这里有任务牌和文字」。

改成不提用途、只描述结果就好了：

```text
整体明度均匀，明暗对比很弱，是一张安静的底。
```

规则：**提示词只描述这张图本身长什么样，不要写它的用途、上下文、将来会叠什么。**

### 4.10 公共段里只能放全体都成立的约束

同一批资产里，桌子要留近黑边给抠图（见 5.5），底纹要四边完全出血——
这两条互斥。第一版把「四边完全出血」放进了公共段，改写时又顺手删掉，
于是首页底纹被画成「白底上躺着一张纸」，四周一圈白边。

**互斥的约束一律写进各条目自己的 desc**，公共段只放全体都成立的东西
（视角、光照、画风）。这和 4.2「气质写进角色自己的描述」是同一条规则的两个面。

## 5. 验收方法

### 5.1 尺寸：逻辑点不是物理像素

wxss 里的 `rpx` 和文档里的尺寸都是**逻辑点**。750rpx = 屏宽，所以 `104rpx` 在
375pt 宽的屏上是 **52pt**。真机把这 52pt 渲染成 `52 × DPR` 个物理像素。

| 资产 | wxss | 逻辑点 | @2x | @3x |
|---|---|---|---|---|
| 任务牌 | `104x154rpx` | 52×77 | 104×154 | 156×231 |
| 身份牌 | `660x880rpx` | 330×440 | 660×880 | 990×1320 |
| 身份牌内插画位 | `168x212rpx` | 84×106 | 168×212 | 252×318 |

**按逻辑点缩图去验收，等于模拟一台不存在的非 Retina 手机，比真机严苛一倍**，
会把本来能用的资产判死。这个错误犯过一次，差点毙掉整条扁平化路线。

### 5.2 验收图必须 1:1，不许放大

`scripts/make-contact.py` 出两张：

| 输出 | 回答什么 |
|---|---|
| `{前缀}_全尺寸.png` | 风格对不对——质感、构图、有没有白角 |
| `{前缀}_真实尺寸.png` | **验收看这张**：真机物理像素下还认不认得出 |

真实尺寸图铺界面底色 `#141c18`（在白底上看深色卡面会严重高估可辨认性），
按 `逻辑尺寸 × DPR` 渲染，**渲染完不做任何放大**。

> 早期干过「先缩到逻辑尺寸、再用最近邻放大 2 倍方便看」——既模拟了不存在的
> 非 Retina 手机，又凭空造出真机上没有的块状模糊。

### 5.3 选片页的图别嵌小了

选片页嵌 300px 却按 300 CSS px 显示，在 Retina 上会被拉到 600 物理像素，糊。
**嵌入宽度 = 显示宽度 × 2**。`build-skin-picker.py` 里 `DISPLAY_W / EMBED_W` 就是干这个的。

Artifact 有 **16MB 上限**。线稿类图（木刻）压缩率比厚涂差很多，同样参数能到 19MB。
`EMBED_W=520, QUALITY=68` 是实测能压进限制的参数。

### 5.4 改完图必须看图

试过把底色校到目标值（`scripts/recolor-cards.py`，**已废弃并加了拦截**），
结果毁掉两套扁平皮肤：逐通道乘性校正的系数是 `目标/实测`，扁平底色的红通道接近 0，
系数爆成天文数字，JPEG 噪点被放大成橙色斑块。

**更坑的是数值检查完全没抓到**：当时只测了「主体金的 97 分位亮度」和「@3x 对比差」，
两个指标都只看主体和边缘，报出「最差 -1 / -14」这种看着很安全的结论——
**底色里长出来的彩色噪点根本不在测量范围内**。

两条教训：

1. 色彩变换不要用逐通道乘性，通道接近 0 时会爆。压饱和度就在 HSV 里只缩 S。
2. **指标能证伪不能证真，视觉复核不能省。**

反例：木刻的套色改色相是安全的（`scripts/recolor-woodcut.py`）——
只写 H、S 和 V 原样保留，数学上不可能放大任何东西。实测纸面最大通道差 1–2，
全图平均明度差 0.09–0.36。但那次用户仍然选择重跑，因为**套色对象本身选错了**，
不是颜色的问题。

### 5.5 近黑底出图 + 抠透明：图标的正解

接口只出 JPEG 没有 alpha。图标要能贴到不同底色上，**不要用纯色背景做色度键**——
色度键在发光/柔边物体上要么留一圈残色、要么啃掉光晕，而且模型会把背景色的环境光
画到物体上（纯绿底会让火焰边缘泛绿）。

正解是**生成在近黑底上**（提示词写「纯净均匀的近黑色，接近 #0a0d0c」），
再用 `scripts/cut-glow.py` 抠。实测三张火球的直方图是干净的双峰：

| | max 通道 | 占比 |
|---|---|---|
| 背景 | ≤ 14（99 分位） | 76% |
| 过渡带 | 20–90 | **0.25%–0.66%** |
| 物体 | ≥ 90 | 19%–23% |

中间只有 0.3% 左右，就是那一两像素宽的抗锯齿边。所以硬阈值分得干干净净。

`cut-glow.py` 有三个模式，**选错会翻车**：

| 模式 | alpha 怎么算 | 适用 | 代价 |
|---|---|---|---|
| `hard`（默认） | 只在 max 通道 18–70 这条窄带上过渡，物体内部一律全不透明 | **亮的平涂图标** | 真正的外发光会被切掉 |
| `lum` | alpha = 亮度，整张图当预乘 alpha 用 | 真发光体（光晕、烛焰） | **暗色部位被判成半透明，只在深色底成立** |
| `flood` | 从画面四边灌连通域，灌到的算背景 | **本身就是暗色的物体** | 物体必须有一圈闭合的亮边界，且不接触画面边缘 |

**亮度类模式在暗色物体上必然失败**，这是原理性的，不是调参数能救的。
深色橡木桌实测 max 通道 18–23，近黑背景 15–26，**两者完全重叠**——
`hard` 的双峰前提在这里不成立（图标的过渡带只占 0.25–0.66%，桌子占 50%）。

`flood` 绕开了亮度：背景是贴着画面边缘的连通区域，从四边往里灌，
灌到哪儿算到哪儿。桌子的**黄铜包边是一圈闭合的亮环**（max 通道 100+），
灌水被它挡在外面，内部的木头再暗也不受影响。

两个前提，缺一个就崩：
1. 物体有一圈**闭合**的亮边界（有缺口就会漏进去，灌满整张图）
2. 物体**不接触画面边缘**——提示词写「外切于画面四边」时要留出余量

`cut-glow.py` 会检查灌水后物体占比是否落在 5%–98% 之外并报错，
这两种崩法都会被抓住。

第一版默认用了 `lum`，在深色底上完美，一贴到白底就露馅：火球最外圈的暗红变成半透明粉色。
原因是亮度当 alpha **分不清「暗色的物体」和「透明」**。改 `hard` 后五种底色全部成立。

反预乘那一步（`RGB / alpha`）正是 5.4 那个「除数趋零系数爆掉」的同款坑，
`cut-glow.py` 把除数钳在 0.25 以上。代价是最淡那圈边略偏暗，深色底上看不出来。

### 5.6 尺寸会变的容器：九宫格，不要按配置各画一张

`.long-table` 的长宽比不是几个预设，是**玩家在座位布局编辑器里现摆出来的**。
`miniprogram/utils/tableLayout.js:79-82`：

```js
const width  = Math.max(top, bottom) ? Math.min(68, 26 + Math.max(top,bottom) * 9) : 32
const height = Math.max(left, right) ? Math.min(62, 24 + Math.max(left,right) * 9) : 28
```

宽只看上下边人数、高只看左右边人数，**两个参数独立**，所以是笛卡尔积：
宽 6 个取值 × 高 6 个取值 = 36 种，扣掉总人数凑不出来的，实际可达 **30 种**，
比值 1.00–2.43（再乘 stage 自身 1.19 的宽高比，真实像素比 **1.19–2.89**）。

按配置各画一张不现实，整图直接拉伸会把桌沿和铆钉抻变形。正解是
**生成一张带完整边框的整图，用 `scripts/slice9.py` 切九宫格**：

| 块 | 怎么变 |
|---|---|
| 四角 | 固定像素，永不缩放——最精致的雕花放这里 |
| 上下边 | 只沿水平方向平铺 |
| 左右边 | 只沿垂直方向平铺 |
| 中心 | `cover` 裁切，只丢边不变形 |

三个实践要点：

1. **边条必须镜像拼贴。** 生成图的边缘不可能天然无缝，直接 `repeat` 会露接缝。
   取一段边条、水平镜像后接上，两倍宽的图块**按构造必然无缝**。
2. **边条内侧要渐隐。** 边条和中心一刀切的话，源图自身的光照梯度会让两边木纹
   亮度对不上，露出一道台阶。内侧 alpha 渐隐 ~18px 就抹平了。
3. **切片尺寸 ≠ 渲染尺寸。** 源图上切 220px 的角，渲染到 630px 宽的桌子上只占几十像素。
   `--inset` 是切片尺寸，`--render-inset` 是落地尺寸（= CSS 给角的 `background-size`），
   后者固定不变，这正是九宫格的意义：桌子再大再小，包边粗细一样。

落地用**多重 background** 就行（9 层，老标准，肯定支持）。`border-image` 能压成 1 行、
切片同一套，但**没在小程序 wxss 里验证过**。

**九宫格能承载的装饰**：四角雕花、四边连续纹样（重复图案天生适合）、
中心无方向性材质、再叠一层内圈线。**做不了的**只有跨越整张的单一大构图
（星象盘、放射光芒这种，每部分都和整体尺寸绑定）。

**中心纹章不要烤进图里**，用独立居中元素（`.table-emblem` 固定 116rpx）：
烤进去的话 `cover` 会让它随容器大小浮动，极端比例还会被裁掉。

> 固定尺寸的容器不受这些约束。`.round-table` 恒为 330×330rpx，
> 所以圆桌整张出图，想画多华丽都行。


### 5.7 合成验收图时，画布不能卡在控件框上

`.seat-badge` 是**故意挂在头像框外面**的——`.game-seat-token` 和 `.seat-badge` 都写了
`overflow: visible`，左上角标的偏移是 `top:-9rpx; left:-2rpx`（负数），右下角标会超出右下边。

拼合成图时按 `72rpx` 开画布，角标就被画布切掉了：皇冠没顶、护身符没底、火焰没尖。
**看上去像抠图抠坏了，其实抠图是好的。** 排查方向搞反过一次，差点去重抠资产。

两条：

1. 合成图的画布要比控件框大一圈（`scripts/build-ui-contact.py` 里的 `SEAT_PAD`）。
2. 怀疑抠图坏了的时候，**先量原图物体的外接框和抠图后的外接框差多少**，
   再看抠图 PNG 顶行/底行的不透明像素数——尖端应该只有个位数。
   实测火球顶行 4 个、皇冠顶行 3 个，尖是完好的，问题就不在抠图。


### 5.8 底纹的花纹尺度要写成数字，不能写「细密」

第一版绒毯实机不成立：一块菱格花约 **63 逻辑点**，而圆桌直径 165 点——
一块花纹是桌子的 38%，整个台面横向只排得下 5 个。这个尺度下它不是「地面材质」，
是「一面有图案的墙」，必然和桌子抢注意力。

提示词当时写的是「极淡的织纹与暗花」——**「淡」和「细」是模糊词，模型自己拿捏**，
拿捏出来的就是这个。改成可验证的具体数字就对了：

```text
毯面上织着一层重复的暗花纹样，横向排得下大约十四个重复单元，每一个都很小。
```

怎么算这个数字：目标是花纹约 25 逻辑点（远小于桌子的 165），
容器 351 逻辑点宽 → 横向约 14 个。**先定「一块花纹该多大」，再除容器宽度得到个数。**

同批还写死了另一条模糊点：「整块毯子明度偏暗，比中调的木头颜色暗一档以上」。
第一版地毯和桌子明度几乎一样，两者糊在一起，桌子不跳。

> **不是所有「不搭」都是资产的问题。** 同一次实机反馈里还有一条是代码的：
> `.round-table` 原本的 `box-shadow` 被误删了。桌面和地面都是正俯视平光，
> 没有投影就完全没有深度线索，桌子看着像贴纸浮在地毯上。
> 收到「不在一个图层」这类反馈时，先分清是**材质问题**还是**深度线索问题**。

## 12. 卡背纹样不能全皮肤共用

第一版给所有皮肤用了同一套纹样（王冠双剑 / 石中剑 / 盾徽），只换渲染——
和角色卡犯的是**同一个错**。剑盾是中世纪通用符号，放在二次元幻想和木刻版画上
都是「借来的」，不是那套视觉语言自己长出来的东西。

**每套皮肤的纹样要从它自己的语言里选：**

| 皮肤 | 纹样 | 来源 |
|---|---|---|
| 幻想华服 | 符文法阵 / 星轨圆盘 / 双翼结晶 | 二次元幻想游戏的原生符号 |
| 木刻线刻 | 命运之轮 / 无尽结 / 沙漏藤蔓 | 中世纪版画传统母题（Rota Fortunae、凯尔特结） |
| 平涂海报 | 几何纹章 / 同心靶 / 层叠山形 | 现代平面设计：纯几何、硬边、无具象 |
| 彩绘胸像 | 玫瑰窗 / 卷草浮雕 / 日轮浮雕 | 木雕能雕的东西 |
| 泥金细密画 | 藤蔓开光 / 金箔十字花 / 葡萄藤 | 手抄本页边装饰 |

三条不变的硬约束：**构图完全对称**、**不能暗示阵营**（未揭示状态，所以木刻的卡背
用中性暗金而不是阵营的靛蓝/暗红）、**要和任务牌背区分**（任务牌用圣杯和圆桌纹章，
身份牌避开这两个）。

## 13. 改 TOML 的时机

`gen-skin.py` **每个任务都重新读一次 TOML**。批次跑着的时候改提示词文件，
后面的任务会用新版本，中途还可能因为结构变化直接报错。

踩过一次：用 `t.index("[back.motifs]")` 截断重写纹样，把追加在文件末尾的
`[variants]` 段一起删了，批次跑到一半开始报 `KeyError: 'loyal'`，
白跑 39 张 ¥23.40。

**两条规则：**

1. **`[variants]` 必须放在 `[back]` 之前**，别追加到文件末尾。
2. **批次跑着的时候不要改它正在读的 TOML。** 要改就等跑完，或者先改再跑。
